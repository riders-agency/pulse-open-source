# Счета и платёжные ссылки

Pulse сохраняет банковский черновик в карточке оплаты: тип операции, плательщика,
ИНН / налоговый номер, назначение и необязательный срок оплаты. Сумма и валюта
берутся из платежа на сервере. Черновик сохраняется между сессиями. Само сохранение
не меняет статус оплаты, не создаёт счёт в банке и ничего не отправляет клиенту.

Кнопка выпуска отключена до подключения проверенного адаптера. Конкретный банк
для подготовки черновика не нужен. Список установленных адаптеров по умолчанию пуст.
Это основа для интеграций; совместимость с конкретными банками пока не заявляется.

## Реализованная граница

- Модуль `clients`: `invoicing` содержит модели и контракт `Provider`, `service`
  проверяет команду, `repository` сохраняет данные, HTTP обслуживает веб-форму.
- `GET /api/v1/payment-actions/{payment_action_id}/bank-invoice` возвращает черновик,
  текущую сумму, статус оплаты, право редактирования и возможности адаптеров.
- `PUT` по тому же пути сохраняет черновик. Обязателен UUID `Idempotency-Key`;
  `revision=0` создаёт первую версию, последующие изменения используют текущую версию.
- Одно атомарное SQL-выражение блокирует оплату и сохраняет черновик. Оплаченные,
  отменённые и нулевые оплаты не принимаются. Конкурирующие записи возвращают 409.
- Повтор последней команды с тем же ключом и содержимым возвращает ту же версию.
  После более нового изменения старый повтор возвращает 409: он не откатывает данные.
  Для каждого нового изменения клиент генерирует новый ключ.
- Сумма хранится в целых минимальных единицах и передаётся строкой; клиент не может
  подменить сумму, валюту или статус через тело запроса.
- Нужны компания и проект пользователя. Для записи через сессию требуется активная
  роль owner, admin, operations_manager, project_manager или finance; ключ API
  ограничивается выданной областью и разрешением write. Чтение не даёт право записи.
- Создание оплаты, ручная отметка оплаты и изменения существующего платежа
  также требуют финансовых/управляющих прав: доступ только для чтения не позволяет
  обойти ограничение черновика через соседние методы API.
- Миграция 114 добавляет отдельную таблицу. Публичная начальная миграция 113 сохранена
  без изменений; исходная закрытая история миграций не публикуется.

## Подключение конкретного банка

Адаптер реализует `Provider.Capabilities`, `Create` и `Lookup`. Он получает
серверную команду с идентификаторами подключения, продавца и ключом операции.
Ключи банка должны оставаться в серверном хранилище секретов. Возможности адаптера
не означают, что банковский аккаунт уже подключён.

Перед включением выпуска нужно реализовать настройку продавца и подключения,
проверку реквизитов, налогов и состава позиций по требованиям конкретного банка,
предварительный просмотр и подтверждение человеком. Сохранение черновика не является
таким подтверждением. ИИ может предлагать данные; Go контролирует применение.

Создание внешнего счёта требует устойчивого журнала операций до сетевого запроса.
После тайм-аута операция остаётся неопределённой до сверки через `Lookup`.
Текущая локальная защита черновиков не заменяет банковскую идемпотентность.
Повторы, срок действия ключей и возможность сверки проверяются по документации банка.

Вебхуки требуют проверки подписи, дедупликации и обработки порядка событий.
Возврат браузера с оплаты не подтверждает поступление денег. Платёжная ссылка,
номер и документ показываются только после подтверждённого ответа провайдера;
отправка клиенту — отдельное действие.

Приёмка адаптера: тестовый контур банка, потеря ответа, повтор команды, чужой проект,
отмена, частичная оплата, поддельный/повторный вебхук и сверка суммы с валютой.
До этого реальная банковская интеграция остаётся выключенной.
